Q1
In a payment system, the delivery semantic that is should be used is Exactly-once.

At-most-once: The message is processed zero or one time. 
Problem: If the consumer crashes after fetching the message but before processing, the payment is lost. The user pays, but the order is never marked as paid. 

At-least-once: The message is guaranteed to be processed, but potentially multiple times.
Problem: If the consumer processes the payment but crashes before sending the acknowledgment (ACK), it will pull the same message again. The user is double-charged ($200 instead of $100).

To implement Exactly-once, we could use:
Idempotency Key: Generate a unique order_id or transaction_id. In the database, use a unique constraint on this ID to ensure the same payment cannot be processed twice.
Transactional Outbox/Atomic Commits: Use Kafka Transactions (PID and Sequence Numbers) to ensure that the message offset is committed only if the database transaction (deducting money) succeeds.

To achieve exactly-once, we would need to either:
Make the processing idempotent (so a second execution does nothing); or
Use Kafka Transactions to commit the offset and the database change together as one atomic unit.

Q8
Watching only the immediate predecessor (the node "before" yourself) is a crucial optimization to prevent the Herd Effect (or Thundering Herd).
The Herd Effect Problem: If 1,000 nodes all watch the same root lock node or the current lock holder, then when the lock is released, ZooKeeper must send 1,000 notifications simultaneously. This can cause a massive spike in network traffic and CPU usage on the ZooKeeper ensemble.
When a node only watches the node "before" itself, when one lock is deleted, only one node (lock-002) receives a notification and wakes up to check if it now holds the lock. 
This ensures the system scales linearly and avoids overwhelming the coordination service.
